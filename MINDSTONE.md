# MindStone Console

This repository is **MindStone Console**, the web interface for [MindStone-Agent](https://github.com/MindStone-Agent/MindStone-Agent). It is a fork of [LibreChat](https://github.com/danny-avila/LibreChat) (MIT), kept close to upstream so upstream fixes can be merged in.

## How the fork is kept

- `upstream` is LibreChat. The fork started at **v0.8.8-rc3**, the version the P0 spike proved against the gateway.
- To take an upstream release: `git fetch upstream tag <tag> --no-tags`, then merge the tag into a branch, resolve, and run the checks in `mindstone/`.
- MindStone changes stay small and listed below, so merges stay cheap. When rebasing costs more than it returns, the fork is severed on purpose, not by drift.
- The design lives in MindStone-Agent `docs/refactor/CONSOLE_DESIGN.md` (#38).

## What MindStone changes

| Area | Change |
|---|---|
| Branding | MindStone diamond as the logo and every icon; page title, PWA name and default `APP_TITLE` are "MindStone Console" |
| Deployment | `mindstone/`: compose file (Console built from this repo plus MongoDB), `librechat.yaml` with the MindStone gateway as the only endpoint, `.env.example` |
| Chat | The MindStone gateway is the only endpoint. Each Console conversation is its own MindStone session, and the user's id, role and conversation id are sent to the gateway as headers. LibreChat agents, presets, memories and model parameters are turned off in `librechat.yaml`. |
| Settings (P2) | A `/mindstone` page for admins: an onboarding checklist, per-section config editing with secrets masked, and the advanced-settings permission. The browser talks only to `api/server/routes/mindstone.js`, which checks the LibreChat session and the admin role, then calls the gateway's admin API with the service token and the admin credential. Neither credential reaches the browser. The proxy allows only listed routes and methods (`mindstone.spec.js`). |
| Setup (#18) | Admins see a dismissible "MindStone isn't set up yet" banner on the chat view while the gateway reports setup incomplete, with a button into `/mindstone/onboarding` (`client/src/components/MindStone/SetupBanner.tsx`, one line in `Chat/ChatView.tsx`). The advanced-settings phrase ignores case and extra whitespace, and a wrong phrase says why the button is disabled. |
| Setup (MindStone-Agent #102) | Guided setup adds three steps after the persona: memory (required: embedding provider and model on the sqlite-vec store, automatic recall on by default, saved only after a live embed check passes, with a model download for Ollama), an optional Telegram, Slack or Discord connector (tokens stored as secrets and cleared from the page when the step is left; owner ids always allowed; no wildcards), and what the agent should know about you. "Start a chat" opens a chat that sends a first hello (`?prompt=…&submit=true`), so the agent answers first. The settings checklist calls connectors optional and links memory and identity to their setup step (`/mindstone/onboarding?step=`). The proxy allows `POST onboarding/complete`, `memory/check` and `memory/pull`; the embed check gets 55 seconds (the model may load first, MindStone-Agent #140) and a model download 16 minutes, past the gateway's own limits. Once the gateway accepts a download, the proxy sends the browser its headers and a newline every 10 seconds until the answer, flushed past compression, so neither the browser (Firefox stops after 5 minutes with nothing) nor a proxy in between gives up; the bundled nginx passes them through unbuffered. A browser that leaves stops the download on the gateway (MindStone-Agent #145). |
| Personas (MindStone-Agent #105) | The Approvals page shows a persona the agent proposes in chat (name, id, description, voice, working style, boundaries) as plain text, never HTML or markdown, with any non-printing character shown as `\u{XXXX}`. Approving it only saves it to the personas; a persona id that already exists is refused with the gateway's text. A `/mindstone/personas` page lists the personas, marks the active one, and is the only place one is made active: **Make active** or **Use no persona** (`PATCH config/personas`, `{ active }`, against the config etag read with the list, so a change made meanwhile is refused). A persona the gateway can't load can't be made active, and both pages say a persona route rule still picks the persona for the chats it matches. The proxy allows `GET personas`. |
| Persona builder (MindStone-Agent #125) | The Personas page builds and edits personas: **Build a persona** and **Edit** open `PersonaEditor` (id, name, description, PERSONA.md text). Its components: skills through Plumb's `SkillPicker` (installed skills; a new one through the Skill Builder and the advanced-settings install), workflows attached in order or built in place (`WorkflowEditor`: route and gate steps, conditions, a persona to hand the turn to, step skills and KBs, attempts, on-fail), global knowledge bases to attach, and the persona's own knowledge bases once it is saved (`PrivateKnowledgebases`: create, add markdown text, add a URL with advanced settings, ingest). A knowledge base the gateway is embedding again after a change of embedding model says so in both lists (`KbReembedNote`, MindStone-Agent #158): found by its words only until the next try, or, once the gateway has given up, a **Try again** that resets it (`POST knowledgebases/<id>/reembed`, or a persona's `…/<kb>/reembed`) so the next owner chat tries again; a refused reset shows the gateway's own text, and a shared KB whose folder name the route can't take (a space, a non-ASCII letter) points to `mindstone kb ingest <id>` instead (MindStone-Agent #164). A connectors slot is shown for later. Saving a persona never makes it active; Make active stays the only switch for personas. Saving a workflow takes effect at once wherever it already runs (the active workflow, a workflow route rule, or a persona that lists it), and the workflow editor says so. Every gateway refusal is shown as given, with non-printing characters visible. The proxy allows `POST personas`, `GET`/`PATCH personas/<id>`, `GET`/`POST workflows`, `GET`/`PATCH workflows/<id>`, `GET knowledgebases`, and a persona's `knowledgebases`, `…/<kb>/sources`, `…/<kb>/ingest` and `…/<kb>/reembed`, and `POST knowledgebases/<id>/reembed`; an ingest gets four minutes, since it fetches the KB's URL sources. |
| Settings parity (MindStone-Agent #140) | Every guided-setup choice can be seen and changed from Settings. **Your setup** (`YourSetup.tsx`) shows the model providers, default model, base persona, memory (embedding provider and automatic recall) and connectors as saved, each with a **Change** link to `/mindstone/onboarding?change=<step>&from=settings`. Setup then opens just that step, filled in with what is saved, with the same controls and requests, saves in place and links back (`from` is `settings` or `providers` only; anything else goes back to Settings). Without `change`, setup is unchanged. The Model providers page links to adding a local provider the same way. **What the agent knows about you** (`AboutYou.tsx`) reads and replaces the default agent's USER.md (`GET`/`PATCH user`, with the etag it was read with, so a file the agent changed meanwhile is never overwritten; advanced settings to save; 64 KiB; non-printing characters shown). Enterprise endpoints show their other sign-in options (Entra ID, AWS roles or keys, workload identity) disabled as not available yet. The proxy allows `GET` and `PATCH user`. |
| Proposed persona components (MindStone-Agent #125) | The Approvals page shows the existing skills, workflows and shared knowledge bases a proposed persona lists, and each new component it brings as its own card (skill, workflow, private knowledge base), marked as part of the persona and shown as plain text. A component card is approved after its persona (the gateway refuses it before, and that refusal is shown); rejecting the persona rejects its components. The persona card's note says a persona sets voice, working style and the components it lists. It says what an empty list means (every installed skill, every shared KB) and shows each listed workflow's steps. A persona's new skill never offers "replace"; its card says approving installs it for everyone who uses all skills. After an approve the page shows what the gateway answered: a KB's ingest count or its ingest error, or a component that isn't in use yet. A decision in flight never touches another card the owner opened meanwhile, and a card that changed anyway (its persona was rejected, the Console stopped waiting) is read again. An approve gets four minutes in the proxy, since approving a KB ingests it; a timeout is a `504 gateway_timeout` ("it may still finish"), a gateway that is down a `502`. |
| Secrets | Store, list and delete stored secrets. Values and sizes are never shown, and Delete is hidden for the gateway's own credentials and for names the store refuses. |
| Approvals | Approve or reject actions the agent proposes. |
| Diagnostics | The gateway's doctor report and its log. |
| Restart | Restart the gateway from the settings page. The gateway checks which supervisor it runs under before exiting. |

## Run it locally

The full, step-by-step install (with checks) is in the README: [Install guide for AI agents](README.md#install-guide-for-ai-agents). The short version:

Use the files in `mindstone/` only. The repo root's `docker-compose.yml`, `deploy-compose.yml` and `.env.example` are upstream LibreChat's: they publish on every interface and allow open registration.

1. Start the MindStone-Agent gateway with chat completions enabled and token auth (its default port is 19789).
2. `cd mindstone && cp .env.example .env`, fill in the secrets and the gateway token. For the settings page, also set `MINDSTONE_ADMIN_TOKEN`, and on the gateway set `gateway.admin.tokenSha256` to its SHA-256, so the gateway never holds the credential itself. Hash it from its file (`printf %s "$(cat <file>)" | shasum -a 256`), never by pasting it. The settings page needs an admin with `read:configs` (to view) and `manage:configs` (to change), platform-wide; the default ADMIN role has both.
3. `docker compose up -d --build`. The page is published on 127.0.0.1:3080 only.
4. Create the admin: `docker compose exec console npm run create-user <email> "<name>" <username>` (it asks for the password). The first account created is the admin, and later ones are users. Registration from the page is off (`ALLOW_REGISTRATION=false`); turn it on only on a network you trust, since the first account to register becomes the admin.
5. Open http://localhost:3080 and sign in.
